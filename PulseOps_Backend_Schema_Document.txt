PurposeThis document defines the backend data model and request/response contracts that implement the locked PulseOps PRD and TRD. It intentionally keeps the MVP small and explainable: no multi-tenant workspace model, no Kafka, no Kubernetes, no autonomous remediation, and no custom ML anomaly detector.

How to use this document
Use the schema tables as the source of truth while implementing the backend. When a later feature needs a new field or table, update this document first, then update the database migration and API contract together so the backend, frontend and documentation remain aligned.

2. Backend Scope and Design Principles
PulseOps receives telemetry from an application that we control, persists the useful evidence, evaluates explicit alert rules, creates incidents when conditions qualify, and serves dashboard data to authenticated users. The backend is a modular monolith: one FastAPI application with clearly separated modules is preferred over many independently deployed services.
Keep the domain model small enough to explain in an interview.
Prefer PostgreSQL as the source of truth for durable operational state.
Use Redis only for background jobs and controlled retries; do not make Redis the primary database.
Persist raw-enough evidence to explain why an alert fired, but avoid building a large log analytics platform.
Use explicit enums/status values so invalid lifecycle transitions can be rejected by the backend.
Never store plaintext passwords or plaintext long-lived service ingest secrets.
AI is advisory and downstream of collected evidence; the AI layer never mutates incident or service state automatically.
MVP boundaryCore loop: telemetry → rule → alert → incident → investigation → resolution. Advanced tooling is phase-gated.

6.1 Incident state machine
OPEN  |  | Start investigation  vINVESTIGATING  |  | Resolve  vRESOLVEDAllowed direct path:OPEN -> RESOLVED
The backend must reject invalid transitions such as RESOLVED → INVESTIGATING in the MVP. Reopening an incident is intentionally outside the first lifecycle contract; a future version can add it as an explicit requirement rather than silently allowing it.
6.2 Alert deduplication rule
When a rule condition is already active for the same service and rule, repeated telemetry updates should refresh the existing alert instead of creating a new alert on every request. The cooldown/active-condition logic lives in the alert evaluation service, not inside the HTTP route handler.
6.3 Incident creation rule
If an alert is configured with create_incident=true and there is no linked active incident for that alert condition, create one incident with status=open, append an incident_events row describing the creation, and make the new incident visible to the dashboard query.

8. Telemetry and Metric Contracts
8.1 Telemetry ingestion payload
{  "service_id": "demo-app",  "timestamp": "2026-10-01T10:30:00Z",  "request_id": "req_8b5d...",  "method": "GET",  "endpoint": "/api/orders",  "status_code": 200,  "response_time_ms": 124,  "outcome": "success",  "error_type": null,  "error_message": null,  "metadata": {}}
Validation rules: service_id must resolve to an active service; timestamp must be ISO-8601; status_code must be between 100 and 599 when present; response_time_ms must be non-negative and bounded to a safe maximum; metadata must remain small and must not contain secrets, credentials or full request/response bodies.

9. Alert Evaluation and Incident Creation
The detection path should be a pure domain flow that can be unit-tested without HTTP: normalize observations → calculate or read metric value → load enabled rules → evaluate threshold → create/refresh alert → optionally create incident → append incident event.
observation   |   vnormalize   |   vmetric value   |   venabled rule match?   |                no               yes   |                | stop       active alert already?                    |                            yes         no                    |            |              refresh alert   create alert                                 |                            create incident?                              |                                     no         yes                                          |                                   create OPEN incident                                          |                                  append incident_event

10. AI Incident Analysis Schema
The AI layer is deliberately downstream from the evidence model. The backend prepares a bounded evidence snapshot containing incident metadata, the triggering alert, recent relevant metrics, recent logs where available, and incident timeline events. The model returns an advisory result that is persisted for reproducibility.

ImportantThe AI assistant must not claim certainty when the evidence is incomplete. The backend UI should visually separate observed evidence from AI-generated interpretation.

Use a secure HTTP-only session or short-lived JWT strategy; refresh design can remain simple in MVP.

Each monitored service receives a random ingest credential once; only its hash is stored.

All dashboard/data routes require an authenticated user; service ingest routes require the service credential.

Database URL, JWT/session secrets and AI provider credentials come from environment variables.

Use Pydantic models for request validation; reject malformed ids and unsupported enum values.

13. Migrations, Seed Data and Retention
13.1 Migration rules
Create schema with an initial migration before application-level seed logic is added.
Never mutate an already-applied migration; add a new migration for every schema change.
Keep enum values explicit in application validation even if PostgreSQL columns use VARCHAR for easier evolution.
Add indexes in the same migration as the feature that requires them and document their query purpose.
13.2 Seed data for local development

13.3 Retention
For the portfolio MVP, keep enough recent telemetry to demonstrate the dashboard and incident workflow without growing unbounded local storage. A simple development default is to retain raw telemetry and logs for 7–14 days, while incidents, alert records and incident_events remain until the user explicitly clears local development data. Exact production retention is outside the MVP scope.
14. Backend Package Structure
backend/└── app/    ├── main.py    ├── core/          # config, security, errors    ├── db/            # session, models, migrations    ├── schemas/       # request/response validation    ├── api/           # auth, services, telemetry, metrics, logs, alerts, incidents    ├── services/      # telemetry, detection, incidents, AI    ├── workers/       # Redis-backed background tasks    └── tests/
This structure separates HTTP routes, validation schemas, persistence models, business logic and background jobs. Do not create a service/repository abstraction for every table unless it makes a real piece of logic easier to test.

15.1 Backend acceptance checklist
A user can register and log in without plaintext password storage.
A service can be registered and receives a one-time ingest credential.
The demo application can send a valid telemetry event.
Malformed telemetry is rejected with a stable validation error.
Metrics and logs can be queried by service and time range.
Alert rules evaluate explicit thresholds and deduplicate active conditions.
A qualifying alert can create exactly one active incident for the condition.
Incident lifecycle transitions are validated by the backend.
Incident events preserve an append-only investigation timeline.
The AI summary can be generated without changing incident state automatically.
All protected user routes reject unauthenticated access.
Schema migrations reproduce the database from an empty PostgreSQL instance.

Source of truthThe backend is correct when application behavior can be followed all the way through the schema: telemetry event arrives → metrics/evidence are stored → rule evaluates → alert exists → incident is created and progresses through a validated lifecycle → the dashboard can read the current state → the AI layer can summarize the collected evidence without inventing operational facts.

Any future schema change should answer three questions before implementation: What user/product requirement requires it? Why can the current schema not support it cleanly? Which migration, API contract, test and documentation changes are required at the same time?
