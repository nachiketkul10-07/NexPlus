1. Implementation objective
PulseOps will be built as a realistic, understandable MVP that monitors an application we control. The implementation must create real monitoring data, detect simple operational problems, surface them in a usable dashboard, turn them into incidents, and later provide an AI-assisted incident summary. The project is intentionally not being expanded into a full enterprise monitoring platform during the initial build.
Objective
What “done” means
Real telemetry
The demo application produces measurable requests, errors and response-time data.
Operational visibility
PulseOps stores and displays service health, metrics, alerts and incidents.
Actionable incidents
A rule can turn abnormal behaviour into an incident with a clear state lifecycle.
Understandable engineering
The code, architecture and decisions can be explained by the project owner in an interview.
Production-minded foundation
Docker, configuration, tests, logging and CI are present without unnecessary infrastructure.

2. Locked scope
Demo FastAPI application with normal, slow and failure endpoints.
PulseOps backend API for services, telemetry, alerts, incidents and assistant requests.
PostgreSQL for durable application data.
Redis for lightweight queue/background processing where required.
React dashboard with the approved Slate Dark visual system.
OpenTelemetry + Prometheus for metrics/telemetry collection.
Docker for repeatable local execution and later deployment.
AI incident assistant only after the non-AI system works.
Tests, documentation, Git workflow and deployment-ready configuration.
Scope guardrailDo not add Kubernetes, Kafka, service mesh, multi-cloud, autonomous remediation, custom ML models or other advanced infrastructure during the core MVP unless a later decision explicitly expands the scope.

5. Detailed implementation sequence
Phase 0 — Project setup
Create the repository and top-level structure before writing feature code.
Create separate frontend, backend, demo-app and infrastructure folders as agreed by the TRD.
Add .gitignore, environment templates, README and basic development scripts.
Choose a single package/version strategy and document it.
Create a baseline branch and first clean commit.
Exit gate: A blank machine can clone the repo and start each component using the documented commands.
Phase 1 — Demo application
Build the FastAPI demo service.
Implement /, /api/health, /api/users, /api/orders, /api/slow and /api/error.
Keep the app intentionally simple; it exists to produce measurable behaviour.
Verify normal, slow and 500-response scenarios manually and with basic tests.
Exit gate: The demo app produces deterministic healthy, latency and failure scenarios.
Phase 2 — Backend foundation
Create FastAPI application package and versioned /api/v1 routes.
Add configuration loading, structured error responses and a health endpoint.
Create service, repository and schema layers only where useful; avoid over-abstraction.
Prepare authentication and role checks for the dashboard users.
Add API documentation through FastAPI/OpenAPI.
Exit gate: Backend starts, health check passes, API docs are available, and core contract tests pass.
Phase 3 — Data layer
Implement PostgreSQL schema from the locked backend schema document.
Create users/roles, services, telemetry records, alerts, incidents, incident events and audit records as applicable to the MVP.
Add primary/foreign keys, unique constraints and timestamps.
Add indexes only for known access patterns.
Add migrations and seed data for local development.
Exit gate: Fresh database can migrate from zero to current schema and pass integrity tests.
Phase 4 — Telemetry
Add the first telemetry contract between the demo app and PulseOps.
Capture request count, status/error signals and response duration.
Persist the minimum data needed for dashboard and alert rules.
Add correlation/request identifiers so events can later be tied together.
Keep the first ingestion path simple before introducing background processing.
Exit gate: A test run can generate telemetry that appears in PulseOps storage and can be queried by service and time range.
Phase 5 — Detection and alerts
Implement simple threshold/rule checks first.
Examples: error rate above threshold, response time above threshold, service unhealthy.
Prevent duplicate alert creation for the same active condition.
Persist alert state and timestamps.
Expose alert listing and detail APIs.
Exit gate: A controlled failure in the demo app creates exactly the expected alert and does not flood duplicates.
Phase 6 — React application shell
Create the approved Slate Dark token system as reusable theme variables.
Build global layout: sidebar, top bar, page container, breadcrumbs/search and notification affordances.
Implement protected routes and loading/error states.
Build reusable cards, badges, buttons, tables, tabs, drawers/modals and charts.
Keep page composition simple and data-driven.
Exit gate: All planned primary routes render with consistent spacing, typography, colours and interaction states.
Phase 7 — Dashboard and service views
Connect Overview cards and charts to live backend data.
Build Services list, service detail, health status and recent telemetry.
Build Alerts list and alert detail.
Add empty, loading and error states.
Add filtering/time-range controls only where backed by APIs.
Exit gate: A developer can go from Overview to a service and see real state and measurements.
Phase 8 — Incident lifecycle
Create incident automatically from a qualifying alert or manually when needed.
Support Open, Investigating, Resolved and Closed states as defined by the flow.
Add timeline/events for acknowledgement, assignment, notes and resolution.
Add incident detail route and deep-link behaviour.
Ensure incident actions are permission-aware.
Exit gate: A controlled outage goes Alert → Incident → Investigating → Resolved with history preserved.
Phase 9 — Async processing and observability
Introduce Redis for tasks that do not need to block request/response.
Move notifications, enrichment or AI-preparation work to background processing where justified.
Add OpenTelemetry instrumentation for the backend and demo app.
Expose Prometheus-compatible metrics and connect dashboard/monitoring views.
Validate service failure behaviour and retry limits.
Exit gate: Background work is observable, bounded and testable; telemetry can show service behaviour end-to-end.
Phase 10 — AI incident assistant
Collect only the incident context allowed by the data contract.
Create a structured AI request containing incident, metrics/log excerpts and recent events.
Return summary, evidence, possible causes and suggested next checks.
Never present AI guesses as confirmed root cause.
Log AI request/result metadata without storing secrets.
Exit gate: An incident can be summarized from real data, with clear evidence and a visible AI/fallback state.
Phase 11 — Hardening and release
Run unit, integration and end-to-end tests.
Containerize services and provide Docker Compose for local setup.
Add CI for lint/test/build.
Check secrets, validation, permissions, rate limits and error handling.
Complete README, architecture diagram, setup guide, demo script and known limitations.
Create release tag and deployment checklist.
Exit gate: Fresh installation, tests, build and demo all pass from documented instructions.

7. Homepage animation implementation specification
Animation requirement — MUST be consistent with the product paletteThe reference video is used only for motion language: deep atmospheric background, floating/centered content, particles, gentle camera movement, focus transitions and staged text/card entrances. The PulseOps implementation must recolour the entire effect to the same Slate Dark + PulseOps primary red/magenta system used in the dashboard; no separate blue/nebula palette should appear on the homepage.

Reference motion direction, translated into PulseOps:
Opening: near-black/slate background with a subtle field of particles or signal pulses.
Brand reveal: PulseOps mark/wordmark enters with a restrained pulse or line-draw effect, not a glowing rainbow treatment.
Hero content: central panel/card enters with slight scale-up + opacity transition and soft depth/parallax.
Ambient motion: small red/magenta particles or signal dots move slowly; motion must never reduce text readability.
Interaction: CTA/button hover uses the same primary colour token; status colours are reserved for status communication.
Transition into the app: hero elements settle and the dashboard/app navigation becomes the visual focus.
Reduced motion: respect prefers-reduced-motion and replace movement with simple fades.

9. Data and API discipline
The PostgreSQL schema is the source of truth for persistent application state.
API request/response models must match the backend schema/data-contract document.
Frontend should consume APIs rather than duplicating business rules in the browser.
Business rules such as alert deduplication and incident transitions belong in the backend.
Every new field or status should be reflected in schema, API model, UI state and documentation before use.
10. AI-assisted implementation workflow
AI coding tools such as Claude or Antigravity may be used for implementation, but the project must remain understandable and testable. The AI tool should receive only one phase at a time and must not be asked to generate the whole system in one shot.
Give the AI tool the locked project context and the current phase only.
Ask it to inspect existing files before changing code.
Require a short explanation of any new dependency or architecture decision.
Run the generated code and tests locally.
Review errors and diffs before asking for the next change.
Update the documentation when the implementation changes an approved contract.
Move to the next phase only after the current exit gate passes.
Non-negotiableThe AI tool is a coding assistant, not the system architect. The architecture, scope, navigation logic and design tokens remain the locked project decisions in this plan.

13. Release and deployment plan
Local: Docker Compose starts PostgreSQL, Redis, backend, frontend and monitoring dependencies.
CI: install dependencies, run lint/tests, build frontend, build backend image.
Environment separation: local/dev values must be separated from deployment secrets.
Deployment: choose one simple hosting path after MVP stability; do not add cloud complexity before the application is stable.
Post-deploy smoke test: health endpoints, auth, service overview, telemetry ingestion and incident creation.

15. Definition of Done
The demo app can generate healthy, slow and failing requests.
PulseOps receives and stores measurable telemetry.
The dashboard reflects live service state and key metrics.
Alert rules detect defined abnormal conditions without duplicate flooding.
Alerts can enter an incident lifecycle with auditable state changes.
Incident details show enough evidence for a developer to investigate.
Homepage animation matches the motion direction of the reference while using the same PulseOps colour system as the rest of the product.
The UI has consistent loading, empty, error, success and reduced-motion states.
Redis/background processing is bounded, observable and tested where used.
OpenTelemetry/Prometheus instrumentation is working and documented.
AI summaries clearly separate evidence from possible causes and support fallback behaviour.
Docker setup and CI work from a clean checkout.
README, architecture, data schema, API contract and demo steps are updated.
The developer can explain the main modules, data flow and failure scenario without relying on generated answers.
