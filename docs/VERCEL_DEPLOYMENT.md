# NexPulse on Vercel

This repository is configured for a Vercel project with three services: the Vite frontend, the FastAPI backend, and the demo application. The root `vercel.json` routes `/api/*` to FastAPI, `/demo/*` to the demo service, and other paths to the frontend. The GitHub integration reads repository metadata; it does not clone or execute a connected repository. Public repositories can be inspected without a token. Private repository access requires a GitHub token entered for that operation.

## Production prerequisites

The backend requires managed PostgreSQL and password-protected Redis. It intentionally rejects local SQLite/Redis and unsafe production settings. Create those resources with a provider and plan that fit your budget, then add their connection URLs as encrypted Vercel production environment variables. No database or Redis resources are provisioned by this repository.

The Vercel team currently has no project or configured data-store integrations. Do not enable a public deployment until the required environment is configured. Vercel Services availability and pricing depend on the team's current plan; confirm the feature is available in the account before creating the production project.

## Vercel environment variables

Add the following in **Project Settings → Environment Variables**, targeting Production. Use encrypted/sensitive values for credentials. Never put secrets in `vercel.json`, Vite `VITE_*` variables, source control, or browser code.

| Variable | Value |
| --- | --- |
| `ENVIRONMENT` | `production` |
| `SECRET_KEY` | New random value, at least 40 characters; generate locally with `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `DATABASE_URL` | Managed PostgreSQL URL using `postgresql+asyncpg://`; URL-encode reserved characters in the password |
| `REDIS_URL` | Managed password-protected Redis URL (`rediss://` preferred where supported) |
| `SESSION_COOKIE_NAME` | `__Host-nexpulse_session` |
| `SESSION_COOKIE_SECURE` | `true` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` (or lower) |
| `ALLOW_PUBLIC_REGISTRATION` | `false` |
| `ALLOWED_ORIGINS` | The exact HTTPS Vercel domain, e.g. `https://<project>.vercel.app` |
| `TRUSTED_HOSTS` | The hostname only, e.g. `<project>.vercel.app` |
| `AI_API_KEY` | A key from the selected AI provider (needed for AI analysis; keep out of frontend variables) |
| `AI_ENABLED` | `true` when `AI_API_KEY` is configured; otherwise `false` |
| `PULSEOPS_INGEST_KEY` | The one-time ingestion key generated by NexPulse for the service identifier `demo-app`; if unset, demo telemetry is disabled |
| `PULSEOPS_INGEST_URL` | The production NexPulse telemetry endpoint, e.g. `https://<project>.vercel.app/api/v1/telemetry/events` |
| `VITE_ENABLE_DEMO_TOOLS` | `true` (public build-time flag; enables the admin demo button) |
| `VITE_PUBLIC_REGISTRATION_ENABLED` | `false` (public build-time flag; keep self-registration disabled) |

Use the deployed hostname for both the two host-related settings. If Vercel assigns a different production alias, include that exact origin and hostname too. GitHub repository inspection for public repos requires no credential; never add a personal GitHub token as a frontend environment variable.

The frontend build uses relative `/api/v1` and `/demo` paths. Do not set an API origin to localhost or expose any backend secret through `VITE_*`.

## Initialize production data and administrator

1. Add the production environment variables to Vercel. Keep public registration disabled.
2. From a private local checkout, place the production `DATABASE_URL` in the ignored `backend/.env` file (never commit it), and set `ENVIRONMENT=production` there. From PowerShell, run `cd backend; alembic upgrade head`.
3. With the same private configuration, run `python -m app.db.bootstrap_admin`. It asks for the administrator email, name, and password interactively; the password is not accepted in command-line arguments or printed. It refuses local databases and refuses to run after any admin exists.
4. Remove the production URL from `backend/.env` when setup is complete. Ensure no local `.env` or credential file is staged.
5. Sign in to NexPulse, register the demo service with identifier `demo-app`, and copy its generated ingestion key once. Add that value to Vercel as encrypted `PULSEOPS_INGEST_KEY`, then redeploy so the demo app can emit telemetry.
6. Enable AI by setting `AI_API_KEY` in Vercel. Without it, the rest of the platform can operate, but AI analysis cannot make provider requests.

Do not run `python -m app.db.seed` in production; it creates development accounts and a known development ingestion key. The bootstrap script creates only the first administrator.

## Deploy and verify

The Vercel Git project should use the repository's production branch and repository root. The checked-in `vercel.json` defines the service roots. Once environment variables and migrations are ready, deploy through the linked Vercel project and verify:

- `/` loads and static client navigation works after a hard refresh.
- `/health` responds over the deployed domain.
- sign-in works and account registration stays disabled.
- a public GitHub repository can be previewed and added; a private one can be accessed only using a user-supplied read-only token.
- the demo service emits telemetry and the resulting events, metrics, logs, alerts, and incidents appear in their views.
- AI analysis works only after a valid provider key is configured.

The previously shared ingestion key must be considered compromised. Do not reuse it; create a fresh service key for production and revoke/delete the exposed one if it still exists.
