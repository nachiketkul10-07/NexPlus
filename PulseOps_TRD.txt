1. Purpose, Scope and Technical Principles
1.1 Purpose
The purpose of the PulseOps TRD is to define how the PRD will be implemented technically. It specifies application boundaries, component responsibilities, data flow, interfaces, storage structures, detection rules, security basics, testing expectations, and the phased build order for the MVP.
1.2 Technical scope
Area
MVP requirement
Demo application
A controllable FastAPI application with healthy, normal, slow, and error scenarios.
Backend
FastAPI/Python service that receives monitoring data, evaluates rules, and manages alerts/incidents.
Frontend
React dashboard for service health, metrics, alerts, incidents, and incident evidence.
Persistence
PostgreSQL for users, services, metrics, alerts, incidents, and incident history.
Async processing
Redis-backed background work for selected jobs and controlled retries.
Telemetry
OpenTelemetry instrumentation and Prometheus metrics foundation in the later monitoring phase.
Containers
Docker-based local execution and reproducible startup in the containerization phase.
AI
Advisory incident summary generated from evidence already collected by PulseOps.

1.3 Technical principles
Explainability first: the core logic must be understandable by a second-year developer.
Incremental implementation: the system is built in the PRD roadmap order and each phase must be testable before the next one starts.
Small architecture: prefer a small number of clear components over a large microservice topology.
Evidence before explanation: alerts and AI summaries must be grounded in actual monitoring information collected by the system.
Safe failure: background failures should not silently destroy important incident data; retry behavior must be explicit.
Configuration over hard-coding: thresholds, credentials, database URLs, and other environment-specific values must be configurable.
No fake scale claims: the MVP is for portfolio/learning use and does not promise enterprise-scale performance, uptime, or compliance.
2. System Architecture and Data Flow
2.1 Logical architecture
Demo FastAPI App        |        | request / health / latency / errors        vTelemetry / Monitoring Layer        |        vPulseOps Backend  |           |  |           +--> Rule Evaluation  |  +---------> PostgreSQL  |  +---------> Redis / Background Worker  |  vReact Dashboard  |  +--> Services / Metrics / Alerts / Incidents  |  +--> Incident Evidence  |  +--> AI Incident Assistant (later phase)

Architecture interpretationThe PRD defines the logical flow as Demo Application → Telemetry → PulseOps Backend → Database / Processing → Dashboard → Alerts / Incidents → AI Assistant. The component boundaries below make that flow implementable without turning the MVP into a large microservice system.

2.2 Runtime data flow
A request reaches the demo application.
The application produces an outcome such as success, slow response, or HTTP error.
The monitoring layer captures the information required by PulseOps.
PulseOps validates and stores the monitoring information needed by the current MVP.
The detection logic evaluates configured threshold rules.
A qualifying condition creates an alert.
A qualifying alert creates or updates an incident.
The React dashboard queries PulseOps APIs and presents the current state plus historical evidence.
The AI assistant can later read the incident context and return a concise advisory summary.

6.2 Rule-based detection
The MVP uses explicit threshold rules rather than black-box anomaly detection. Thresholds should be configurable so that the same engine can be tested against the demo application without changing code.
Example rule
Condition
Result
High error rate
Error rate > configured threshold for the evaluation window.
Create alert for the affected service.
High latency
Response time > configured threshold.
Create alert for slow-response condition.
Unhealthy service
Health check fails or returns an unhealthy state.
Create alert for service health.

6.3 Alert deduplication
Repeated observations of the same underlying condition should not create an unlimited number of identical alerts. The MVP should use a simple deduplication key such as service + rule name + currently active condition. The implementation must document its exact behavior.

7.3 Redis worker and retries
Redis is introduced only after the synchronous monitoring workflow is working. At least one background operation must be demonstrable with a controlled failure scenario.
Requirement
Technical behavior
Queueing
API places an allowed background task onto a Redis-backed queue.
Worker
A worker receives the task and performs the operation outside the request path.
Retry
A failed task is retried according to a bounded retry policy.
Failure visibility
After retries are exhausted, the failure must be observable rather than silently discarded.
Idempotency
Retrying the same logical task must not create an unintended duplicate incident or event.

9. AI Incident Assistant
9.1 Purpose
The AI layer is advisory. It summarizes an incident using evidence already collected by PulseOps and may suggest possible contributing factors. It does not fix application code or infrastructure and does not replace the monitoring/detection logic.
9.2 Input context
Incident title, status, severity, and timestamps
Affected service
Triggered alert and rule
Recent metrics relevant to the alert
Recent incident events
Relevant logs or telemetry available at the time of implementation
9.3 Output structure
{  "summary": "Concise explanation of what happened",  "evidence": [    "Observed metric / error facts"  ],  "possible_causes": [    "Potential contributing factor"  ],  "confidence_note": "Advisory; validate against the evidence"}

AI safety rule for the MVPThe assistant must clearly separate observed evidence from possible explanations. It must not present a guessed root cause as a verified fact.

16.3 Glossary

Meaning

Final technical definitionPulseOps MVP is a small, explainable system in which application behavior produces telemetry, the backend evaluates explicit rules, alerts become trackable incidents, the dashboard presents evidence for manual investigation, background jobs demonstrate controlled asynchronous behavior, and the AI layer provides an advisory summary only after evidence exists.
